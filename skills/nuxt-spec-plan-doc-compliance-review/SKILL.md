# Auditing a Nuxt spec/plan against Nuxt docs

Two halves: (A) doc compliance — does each proposed mechanism match a documented idiom; (B) factual grounding — do the plan's claims about the app's own structure hold. Do both; a compliance verdict on wrong facts is worthless.

## A. Doc-compliance axes (check each, and credit the matches)

Fetch live docs — training-data Nuxt knowledge is stale. `/docs/4.x/guide/concepts/rendering`, `/docs/4.x/directory-structure/app/middleware`, `/docs/4.x/guide/recipes/sessions-and-authentication`, `/docs/4.x/api/utils/define-page-meta`, `/docs/4.x/directory-structure/shared`, `/docs/4.x/guide/going-further/experimental-features`.

1. **Route rules for SSR gating** — `routeRules: {'/admin/**': {ssr: false}}` is the sanctioned idiom (the rendering doc's own example). Per-route `ssr:true` override below a `ssr:false` catch-all is documented. **Caveat the plan may miss:** hybrid rendering requires a *server* output — check the Dockerfile/CD for `nuxt build` + `.output/server/index.mjs` + `NITRO_PRESET=node-server`. If deploy is `nuxt generate`/static, route rules silently don't work. Also: a client-only route also excludes its component from the server bundle — a build-size win the author may not have noticed.
2. **`ssr:false` wants `spa-loading-template.html`** — the rendering doc: *"If you do use `ssr: false`, you should also place an HTML file in `~/spa-loading-template.html`."* An app-wide `ssr:false` default without this file means a blank first paint. Commonly omitted from plans; flag it as a missing artifact, not a performance opinion.
3. **Global middleware ordering** — numeric filename prefix (`00-`, `01-`) is documented ("Ordering Global Middleware"), including the note that filenames sort as *strings* (`10.` before `2.`).
4. **`process.server` vs `import.meta.server`** — every middleware example in the docs uses `import.meta.server`/`import.meta.client`. If a plan copies `process.server` from legacy Nuxt-2-compat files into *new* code, grep the repo for `import.meta` first: if a newer precedent exists in-tree, the right verdict is "match it; treat the legacy files as pre-existing debt," not "match the existing files."
5. **`pages:extend` hook** — the middleware doc has a section literally titled *"Setting Middleware at Build Time"* with a recursive `hooks['pages:extend']` that sets `page.meta.middleware` over the whole page tree. When a plan proposes hand-maintained allow-list/protected-route manifests plus an fs-walking completeness test, this hook is the documented alternative that makes drift structurally impossible. Weight it heavily in the recommendation.
6. **`shared/` for cross-context code** — code used by both the Vue app and Nitro belongs in `shared/utils/`. Relevant because `nuxt.config.ts` is loaded by **jiti**, not Nuxt's app resolver: a constant imported into the config from `app/utils/` must be dependency-free (no `~`/`@` alias, no auto-imported composables) or config load breaks. Verify by grepping sibling files in that dir for `@/`/`~` imports — if the pattern is live, the constraint is real and must be stated.
7. **Client gate is UX, not authorization** — the auth recipe: *"Client-side middleware is helpful for the user, but without server-side protection your data can still be accessed."* After `ssr:false` an anonymous request still gets `200` + empty shell. If the spec does not say plainly that the real boundary is the API, flag the omission — that's what a future reader "fixes" by re-enabling SSR.
8. **Non-issues to credit rather than flag** — when auth is external (Keycloak/OIDC) with browser-held tokens to a separate API, the absence of `nuxt-auth-utils`/`requireUserSession` is *not* a violation: Nitro holds no session to validate, and adopting the recipe is a re-architecture. The transferable principle (data routes server-protected) is what matters. Say so explicitly so the report doesn't read as idiom-checklist slop.

## B. Grounding the app's own claims

- **Counts.** `find app/pages -type f -name '*.vue' | wc -l` (total) and `grep -rl 'definePageMeta' app/pages --include='*.vue' | wc -l` (files with meta). These two numbers legitimately differ and specs often conflate them — say which is meant. Beware stale-shell artifacts: if a `find`+`grep` count disagrees with a scoped `-type f` count, re-run with a distinct command before reporting a discrepancy.
- **Ungated pages.** A page is gated if its own `definePageMeta` names `auth`/`admin`, or a global middleware covers its prefix, or a **parent** route record's middleware applies. Do not infer the last from directory structure — see the nesting trap.
- **Route nesting trap (verify empirically).** Nuxt only nests page records when the parent file contains `<NuxtPage/>`. With no such component, every page is a **flat top-level route**, `to.matched` never includes the parent, and a parent's `definePageMeta({middleware})` does **not** gate its children. Confirm against the **generated route table**, not source: in `.output/public/_nuxt/*.js`, find `name:"<route-name>"` records; records carrying a `children:` key are nesting parents (filter out false positives — `children:` also appears in Vue internals like `Teleport`/`BaseTransition`). A sub-page record with no `meta:{middleware:...}` and no `children:` ancestry is genuinely ungated.
- **`routeRules.appMiddleware` cannot disable a global middleware.** In `node_modules/nuxt/dist/pages/runtime/plugins/router.js` the entry set is seeded with guard **objects** (`[...globalMiddleware, ...nuxtApp._middleware.global]`), while `appMiddleware[k]=false` calls `Set.delete(<string>)` — a no-op against objects. It only adds/removes **named** middleware. So `{'/login': {appMiddleware: {'00-protected': false}}}` will never let a `.global` gate skip `/login`. Don't recommend it as a fix for a global gate; it *is* a viable simplification for page-level named declarations.
- **`process.client`/`process.server` in non-middleware code** (stores, components) is a separate, larger surface — grep `app/` for both `process.` and `import.meta.` before making claims about which idiom the repo uses.
- **Leak surface.** Grep for `useAsyncData`/`useFetch(` in `app/pages/`. Zero hits means SSR emitted only synchronously-rendered markup — the exposure is UI shell + statically-imported mock data, not server-fetched customer data. Trace the mock module's import chain (page → component → data file) to say what actually leaks.
- **Cookie/SSR feasibility.** If a plan claims server-side session validation is impossible for a separate-host Nuxt server, verify the cookie flags in the API: a `Domain` derived from the API's own hostname means the Nuxt server never receives the cookie. Also check the CORS setup's environment gating — CORS registered only when env == local means deployed tiers have none.

## Report shape

Lead with the verdict, then a **matches** table (credit the sanctioned idioms, with the doc quote), then **deviations** ranked by value, then a **fact-check** table with `claim — verdict — evidence`, then **recommendations** ranked. End with the explicit non-issues. Separate "the plan violates a documented idiom" from "the plan states a wrong reason for a right conclusion" — the latter is a wording fix, the former a design fix.
