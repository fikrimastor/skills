# Verified capability-guideline corpus

Producing reference docs for a registry with 100+ capabilities. The failure mode is
hand-written "verified output" that no one can re-check. Invert it: build a
committed generator first, then write prose around its output.

## Phase 0 — ground the contract (never parse the big YAML)

Look for a public describe/contract API and drive everything from it:

```python
from plotting_core import describe_capability
# required_canonical_columns, input_alternatives,
# derived_metrics[].human_equation (recursive), preparation_options, example_request
```

If the library has one, it is authoritative and sync-safe — do not hand-parse a
600KB `domain/*.yaml`. Enumerate via `list_capabilities()`; treat any doc/notebook
cached count as stale (a notebook claiming 118 was really 128).

## Phase 1 — build a physically-valid fixture

A "demo" sample is not a fixture. Audit it for degenerate values and repair them:

- aliased pressure columns (`reservoir_pressure == bottomhole_pressure`) → zero
  drawdown → every PI/injectivity/Hall metric NaN → empty plot
- constant/absent day counters → derivative denominators collapse
- missing coordinate columns for map engines
- missing static description columns (ooip/area/porosity/pay/Sw)
- absent fluid types (e.g. no oil/gas injection) → those capabilities plot nothing

Repair in a `build_fixture()` wrapper you own. Record each repair as a **trap on
real data too**, since the same shape occurs in production data.

## Phase 2 — committed generator + gate

Add `outputs/export_<name>.py` exposing `build_fixture()`, `digest(response)`,
and a `--check` mode that FAILS when any capability errors or plots nothing.
Write the fact pack (per-capability contract + measured digest) to JSON next to the
docs. This is what makes the corpus re-verifiable; without it the docs rot into
unverifiable assertions.

```bash
PYTHONPATH=. python -m outputs.export_capability_guidelines --check
# 128 capabilities across 16 families / error diagnostics: 0 / empty plots: 0
```

Encode option rules IN the generator so examples are correct by construction —
e.g. only pass `level` for aggregating families, and never for coordinate/axis
engines, because `level` routes preparation through domain aggregation which drops
non-metric columns (coordinates, day counters) and empties the plot.

## Phase 3 — structure the corpus by engine, not one file per family

Near-identical families (same metric set at different aggregation levels) must
share ONE chapter with a level matrix. Emitting 16 near-duplicate family docs is
4x duplication that drifts. Aim for ~6 chapters grouped by what the user is
trying to draw.

Chapter contract, fixed section order:
`At a glance` (every capability — the completeness gate) -> `ELI5` -> `Why this
exists` -> `Inputs you must supply` (with the diagnostic code per missing input)
-> `How each capability is computed` (exact equations) -> `Runnable examples`
(measured output after each) -> `Traps and failure modes` -> `API calls` ->
`Source of truth`.

Write the shared-contract README yourself (pipeline, full option reference,
response envelope, diagnostics table, units, global traps). Chapters link to it
and must not restate it.

## Phase 4 — fan out, cap concurrency

One writer per chapter, each given: its fact-pack slice, the fixed section order,
the rule "quote `verified.*`, never invent output", and the fixture traps. Respect
the concurrency cap — over-dispatching silently drops the excess writers and you
will not notice until files are missing.

## Phase 5 — verify like an auditor

- coverage: every capability id present, cross-chapter overlap zero
- equations: every `human_equation` string appears in its chapter
- diagnostic codes: cross-check each cited code against the source registry
- **execute every HTTP body in the corpus** end to end (FastAPI `TestClient`) —
  this catches schema-shape errors that read fine and 500 at runtime
- independently re-run each chapter's numbers; writers may be quoting a different
  option set than you assume. When a writer disputes your figure, re-measure before
  insisting — they were right about a trace count I had taken from a stale run.

## Traps that generalise

- Nested vs top-level request fields: a request field that also exists as a render
  option can collide when nested, producing a 500 (duplicate keyword argument).
  Copy the registry's `example_request` only if it matches the transport shape —
  library-shaped examples omit the transport envelope.
- Aggregation steps silently drop columns outside the requested metric set.
- A "demo" dataset is the single largest source of "my plot is empty" reports.

## Closeout

Fold any superseded single-family doc into the corpus and leave it a pointer.
Refresh the repo graphs if the repo requires it. If the repo mandates an
architecture tool for specs/plans, note that a reference-documentation deliverable
is out of that rule's scope — the markdown's own mermaid diagram already
materialises the pipeline.
